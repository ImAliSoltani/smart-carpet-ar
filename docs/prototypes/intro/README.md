# نمونه‌های ورودی سینمایی

چهار الگوی تعامل ساخته و کنار هم مقایسه شد. `chaptered.html` الگوی انتخاب‌شده و تنها نسخه‌ی به‌روز است؛ سه تای دیگر برای ثبت مقایسه نگه داشته شده‌اند و در محصول نهایی به کار نمی‌روند.

| فایل | الگو | نتیجه |
|---|---|---|
| `chaptered.html` | صفحه قفل، هر اسکرول یک فصل را پخش می‌کند و روی صحنه‌ی بعدی می‌ایستد | **انتخاب شد** |
| `snap.html` | اسکرول آزاد، پس از توقف به صحنه‌ی بعدیِ هم‌جهت می‌چسبد | نامزد دوم |
| `scrub.html` | فریم تابعی از موقعیت اسکرول (الگوی رایج، مشابه اپل) | رد شد — حس فیلم نمی‌دهد |
| `video.html` | ویدیوی خودپخش | رد شد — بازدیدکننده نقشی ندارد |

## آنچه در `chaptered.html` تثبیت شده

هر یک از این‌ها پس از دیدن یک مشکل واقعی اضافه شد، نه از پیش:

**توقف روی صحنه‌های انتخاب‌شده.** فریم‌های `0, 38, 75, 105, 136`، یافته‌شده با تطبیق پنج تصویر ثابت روی فیلم. توقف در فاصله‌های مساوی، وسط حرکت می‌ایستاد.

**اسکرول وسط پخش گم نمی‌شود.** پخش شتاب می‌گیرد و آن حرکت در صف می‌ماند تا بلافاصله اجرا شود.

**قفل آماده‌سازی.** تا اسکلت فصل اول نرسیده، اسکرول پذیرفته نمی‌شود و درصد پیشرفت نشان داده می‌شود. بدون این، هر که زودتر اسکرول می‌کرد پخش پرش‌دار می‌دید.

**رمزگشایی خارج از رشته‌ی اصلی.** فریم‌ها با `createImageBitmap` آماده می‌شوند، نه با `<img>`؛ رمزگشایی AVIF آن‌قدر سنگین است که همان انیمیشنی را که تغذیه می‌کند می‌لرزاند.

**آزادسازی حافظه.** هر فریم رمزگشایی‌شده‌ی ۱۹۲۰ حدود ۸ مگابایت حافظه می‌گیرد؛ نگه داشتن هر ۱۳۷ تا از یک گیگابایت می‌گذرد. فقط فریم‌های نزدیک نقطه‌ی فعلی می‌مانند.

**عقب نگه داشتن تصاویر فروشگاه.** تصاویر شبکه‌ی محصولات تا پایان ورودی درخواست نمی‌شوند. رها شده، پیش از فریم‌ها دانلود می‌شدند و پهنای باند را می‌بلعیدند — روی اتصال کند این تنها عامل، آماده‌سازی را از ۲۰ ثانیه به چند دقیقه می‌برد.

**اجرا فقط یک بار در ۲۴ ساعت.** تصمیم پیش از نخستین رنگ‌آمیزی صفحه گرفته می‌شود تا ورودی چشمک نزند. `?intro=1` همیشه اجرایش می‌کند (برای روز دفاع)، و دکمه‌ای در انتهای فروشگاه آن را دوباره پخش می‌کند.

**بازگشت به تصویر ثابت روی اتصال کند.** ابتدا از مرورگر پرسیده می‌شود، و مستقل از آن پنج ثانیه بودجه گذاشته می‌شود: اگر اسکلت فصل اول در این مدت جمع نشد، فیلم رها می‌شود و فرش کامل به‌صورت ثابت با نام برند نشان داده می‌شود. فایرفاکس آن API را ندارد، پس اندازه‌گیری تنها راه قابل اتکاست.

## حجم — اندازه‌گیری‌شده، نه تخمینی

| ست | حجم کل | هر فریم | PSNR |
|---|---|---|---|
| webp-1920 (نقطه‌ی شروع) | ۱۸٫۴ م.ب | ۱۳۸ ک.ب | ۳۹٫۵ |
| avif-1920 (صحنه‌های توقف) | ۱۳٫۹ م.ب | ۱۰۴ ک.ب | ۴۰٫۷ |
| motion-1280 (میانی، دسکتاپ) | ۴٫۹ م.ب | ۳۷ ک.ب | ۳۶٫۰ |
| motion-960 (میانی، موبایل) | ۳٫۴ م.ب | ۲۶ ک.ب | ۳۴٫۳ |

AVIF هم کوچک‌تر است هم PSNR بالاتری دارد — یعنی همان تصویر با بایت کمتر، نه تصویری بدتر.

فریم‌های میانی افت اندازه‌پذیر دارند اما در مقایسه‌ی چشمی کنار هم تفاوتی دیده نشد، چون هرکدام کسری از ثانیه و در حال حرکت روی صفحه‌اند. صحنه‌های توقف — جایی که چشم می‌ایستد — دست‌نخورده‌اند.

**تا نخستین اسکرول:** حدود ۷۰۰ کیلوبایت روی دسکتاپ و ۴۲۵ کیلوبایت روی موبایل، در برابر ۱۸ مگابایت در نقطه‌ی شروع.

## بازتولید

دارایی‌های سنگین در گیت نیستند.

```bash
uv run --group ml python backend/scripts/extract_intro_frames.py assets/<film>.mp4 docs/prototypes/intro/frames2 137
```

اگر فیلم عوض شد، صحنه‌های توقف را به‌صورت تصویر در `assets/` بگذارید و شماره‌ی فریم‌ها را بگیرید:

```bash
uv run --group ml python backend/scripts/find_intro_stops.py assets/<film>.mp4 assets docs/prototypes/intro
```

خروجی در `STOPS` داخل `chaptered.html` جایگزین می‌شود. یک تصویر مقایسه‌ای هم می‌سازد تا از درستی تطبیق مطمئن شوید.

چند تصویر فرش از `data/catalog-seed/cutouts/` را کنار فایل‌ها بگذارید و پوشه را با یک سرور ساده بالا بیاورید — باز کردن مستقیم از روی دیسک، بارگذاری فریم‌ها را مسدود می‌کند:

```bash
python -m http.server 8123
```

## سوییچ‌های آزمایش

| پارامتر | کار |
|---|---|
| `?intro=1` | اجرای اجباری، حتی اگر پیش‌تر دیده شده باشد |
| `?mode=hybrid` | فریم‌های میانی سبک (پیکربندی نهایی) |
| `?set=webp-1920` | تحمیل یک ست مشخص، برای سنجش هزینه‌ی رمزگشایی |
| `?force=static` | آزمودن حالت اتصال کند بدون throttling |

**نکته‌ی مهم هنگام آزمایش:** throttling مرورگر فقط وقتی اعمال می‌شود که DevTools باز باشد. با بستن آن، همه‌ی سنجش‌ها روی شبکه‌ی کامل انجام می‌شود و بی‌اعتبار است.

## باقی‌مانده برای فاز ۳

- مسیر خروج برای کیبورد و صفحه‌خوان، چون اسکرول در این الگو قفل است.
- انتقال از نمونه به Next.js با همان قواعد.
- بررسی WebCodecs به‌عنوان بهینه‌سازی احتمالی: خواندن فریم‌ها مستقیم از فایل ویدیو، فشرده‌سازی زمانی را برمی‌گرداند و حجم را حدود یک‌چهارم می‌کند. پیچیده‌تر است و نیازمند همین دنباله‌ی تصویر به‌عنوان پشتیبان.
